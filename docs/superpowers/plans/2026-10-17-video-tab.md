# Video Tab Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a Video mode. You pick start and end photos, write a prompt, see the exact price before generating, and the clip renders in the background with a notification when it's done. It also adds video models to the Library and a Video view to Stats.

**Architecture:** This reuses everything the Images plan built, with `kind = 'video'`: threads, `media_models`, `media_catalog_cache`, `media_generations` and `media_events`. What's new:
- a pricing parser for `pricing_skus`
- an asynchronous job flow: submit, a server-side poller, then download the clip to disk
- a Range-capable video file route
- frame-slot composer UI

**Tech Stack:** TypeScript, Hono + better-sqlite3, React 19 + Vite, Vitest (node only).

**Spec:** `docs/superpowers/specs/2026-10-17-video-tab-design.md`

**Prerequisite:** the Images plan (`2026-10-17-images-tab.md`) is done.

## Global Constraints

- Flow:
  - `POST /api/v1/videos` returns 202 with `{ id, polling_url }`. The `polling_url` may be relative or absolute.
  - `GET /api/v1/videos/{id}` gives the status: `pending` / `in_progress` mean still running; the final ones are `completed`, `failed`, `cancelled` and `expired`.
  - `GET /api/v1/videos/{id}/content?index=0` downloads the clip, with the API key.
- **Always send `generate_audio: false` unless sound is on.**
- Defaults: the shortest duration, `720p` (or the lowest offered when 720p isn't), sound off, the aspect from the start photo snapped to a supported ratio (else `16:9`).
- Polling: every 30 s for the first 30 min, then every 5 min. It **never gives up on its own**, and stops only at a final status. On startup, every `rendering` job is checked immediately.
- Out of scope, so hidden from the catalog: FLUX Video Edit, FLUX Video Upscale, Runway Aleph 2, HeyGen Avatar IV, and any model with no `supported_durations` and no `supported_frame_images`.
- Prices are exact when the SKU parser understands every applicable key. Seedance token pricing is shown with `~`, and unknown applicable keys mean "Price after generating" / "Price unknown". Nothing is guessed silently.
- Clips are stored on disk at `<dirname(db file)>/videos/<assistantMessageId>.mp4`, and deleting a thread deletes its files.
- One render per thread at a time. Other threads render in parallel.
- Commits and the 3100/5174 test-instance rules are the same as in the other plans. **Every paid call needs the user's go-ahead first.**

## Review Focus

1. **A clip finishes while OpenChat is shut down.** On the next start, the job is checked at once and the clip is downloaded, never lost. Pinned in Task 4 (`resumes after restart`).
2. **The download fails after `completed`** (network, or a 401 from a changed key). The message must stay `rendering` and the download must be retried on the next poll, not marked as an error, because the user paid. Pinned in Task 4 (`retries a failed download`).
3. **Seeking in the player.** The browser sends `Range` requests, and without 206 support it can't scrub. Pinned in Task 4 (`serves byte ranges`).
4. **The model changes after photos are filled**, and the new model only has `first_frame`. The End slot must be disabled and the end photo left out of the request (kept in the slot, greyed). It must not be silently sent. Pinned in Task 1 (`buildVideoRequest drops last frame`).
5. **A thread is deleted while rendering.** The poller keeps polling the job and logs the event (paid) with a null message, deletes the downloaded file, and doesn't throw. Pinned in Task 4 (`thread deleted mid-render`).

### Task 1: Video catalog parsing, pricing and requests (pure)

**Files:**
- Create: `shared/videoModels.ts`, `shared/fixtures/video-models.json` (the live response)
- Test: `shared/videoModels.test.ts`

**Interfaces:**
- Produces:
  - `interface VideoModel { id; name; description; created: number | null; durations: number[]; resolutions: string[]; aspects: string[]; sizes: string[]; frames: { first: boolean; last: boolean }; sound: boolean; skus: Record<string, string> }`
  - `parseVideoModel(entry: any): VideoModel | null`. It returns null for the out-of-scope models.
  - `interface VideoSettings { duration: number; resolution: string | null; aspect: string; sound: boolean }`
  - `defaultVideoSettings(m: VideoModel, startPhotoAspect: number | null): VideoSettings` and `snapVideoSettings(m, s): VideoSettings`
  - `videoPrice(m: VideoModel, s: VideoSettings, photos: number): { cost: number | null; estimated: boolean; perSecond: number | null; breakdown: string; nextSteps: { label: string; extra: number }[] }`
    - `breakdown` example: `"5s × $0.084/s at 720p = $0.42"`
    - `nextSteps` example: `[{label:'sound', extra:0.21}, {label:'1080p', extra:…}]`
  - `cheapestPerSecond(m: VideoModel): number | null`. This is for the card's "from $0.03/s".
  - `buildVideoRequest(m: VideoModel, s: VideoSettings, prompt: string, frames: { first: string | null; last: string | null } /* data URLs */): object`. It always includes `generate_audio: s.sound` when `m.sound`, and drops a frame the model doesn't support.
- **SKU rules** (decide each key independently):
  - `cents_*` is ÷100, and other keys are dollars.
  - A resolution suffix (`_480p`, `_720p`, `_1080p`, `_2k`, `_4k`, lowercased) applies to that resolution only. Keys without one apply to every resolution that has no specific key.
  - `image_to_video_*` applies when there's a start photo, `text_to_video_*` when there isn't, and the plain form applies to both.
  - `*_with_audio` / `*_without_audio` select on sound. When only `with_audio` exists and sound is off, use the plain key.
  - `cents_per_image_input` is added once per filled slot.
  - `minimum_cents_per_generation` is a floor.
  - These are ignored: `reference_*`, `*_video_continuation_*`, `video_tokens_with_video_input`, `cents_per_megapixel_second_*`.
  - `video_tokens` / `video_tokens_without_audio` give an estimate of `rate × w × h × 24 × duration ÷ 1024`, from the chosen `size` (or the first size matching the resolution and aspect).
  - Any other key that could apply makes `cost: null`.
- [ ] **Step 1: Write the failing tests** against the fixture:
  - Kling 3.0 Std, 5 s 720p, sound off, with a start photo: `0.42`, exact, `breakdown === '5s × $0.084/s at 720p = $0.42'`, and the sound next step `+0.21`.
  - Veo 3.1 Lite, 4 s 720p, sound off: `0.12`.
  - Grok Imagine Video 1.5 Lite, 4 s 480p, 1 photo: `4 × 0.02 + 0.01 = 0.09`.
  - Hailuo 3 Max at 480p: `duration_seconds_480p` beats `duration_seconds`.
  - Seedance 2.5, 5 s, `1280x720`: estimated, `≈ 0.0000107 × 1280 × 720 × 24 × 5 / 1024`.
  - An unknown applicable key gives `cost: null`.
  - FLUX Video Upscale gives `parseVideoModel === null`.
  - `defaultVideoSettings(Kling Std, 4/3)` gives `{ duration: 3, resolution: '720p', aspect: '1:1' or the nearest supported ratio, sound: false }`. Assert the nearest by the absolute difference of ratios.
  - `buildVideoRequest drops last frame` for a first-frame-only model, and always contains `generate_audio: false` when sound is off.

### Task 4: Video jobs, poller and file serving

**Files:**
- Create: `server/src/videoJobs.ts`, `server/src/routes/videos.ts`
- Modify: `server/src/app.ts` (`Deps` gains `mediaDir: string`; `index.ts` passes `join(dirname(dbFile), 'videos')`, and tests pass a temp dir), `server/src/index.ts` (start the poller), `server/src/chats.ts` (`deleteChat` removes the thread's clip files)
- Test: `server/test/videoJobs.test.ts`

**Interfaces:**
- Consumes: `buildVideoRequest`, `videoPrice`, `snapVideoSettings` (Task 1); the client (Task 2); the tables (Images Task 1); `resolveAttachmentIds` (frames from attachments).
- Produces:
  - `POST /api/chats/:id/videos` with body `{ prompt; modelId; settings: VideoSettings; startAttachmentId: string | null; endAttachmentId: string | null; parentId?: string }`. It returns `202 { userMessageId, assistantMessageId }`, gives 409 when the thread is busy, and gives 400 for an unsupported setting or frame. It saves the assistant message as `rendering`, and `media_generations` gets `job_id`, `settings` and `started_at`.
  - `createVideoPoller(deps, { now = Date.now, schedule = setTimeout }): { tick(): Promise<void>; start(): void; stop(): void }`. `tick` checks each unfinished video job that's due (30 s cadence for the first 30 min since `started_at`, then 5 min).
    - **On `completed`:** stream the download to `mediaDir/<messageId>.mp4.part`, rename it to `.mp4`, then set the message `complete` and record `media_events` (`seconds = duration`, cost from `usage.cost`, otherwise `videoPrice` with `cost_estimated = 1`). A failed download leaves the job due again.
    - **On `failed` / `cancelled` / `expired`:** set `error` with the reason, and record the event (cost from usage, else 0).
    - **Thread gone:** record the event with a null message and delete any file.
    - `start()` runs one tick immediately (the restart resume), then reschedules.
  - `GET /api/videos/:messageId` serves the file with `Content-Type: video/mp4`, `Accept-Ranges: bytes`, `206` for `Range` requests, and 404 when missing.
  - `ChatSummary.busy` already covers `rendering`. `ChatDetail.generations` entries gain `jobStatus: string | null` and `startedAt`.
- [ ] **Step 1: Write the failing tests** with a scripted fake client and an injected `now`:
  - `completes and logs`
  - `failed job logs reason`
  - `slows to five minutes after thirty` (not due at +2 min after 31 min; due at +5 min)
  - `never gives up` (still polling at +3 h)
  - `resumes after restart` (a new poller over the same DB downloads on its first tick)
  - `retries a failed download`
  - `thread deleted mid-render`
  - `serves byte ranges` (`Range: bytes=0-9` gives 206 with 10 bytes and a `Content-Range`)
  - `deleteChat removes clip files`
